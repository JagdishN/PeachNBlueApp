## What this app is

A staff + admin operations app for a hyperlocal laundry/ironing business (Peach & Blue), branded but built and maintained by NIVENXA. React Native, Android + iOS, single codebase, two role-based views.

**There is no customer-facing app.** Customers contact the business only by phone call or WhatsApp, and receive all updates (pickup confirmation, amount revisions, delivery confirmation, receipts, monthly statements, reminders) via **WhatsApp only** (see "Messaging migration — MSG91, WhatsApp-only" below — SMS was removed, this supersedes the original "WhatsApp and SMS" design) — never through an app UI. Do not build customer login, customer screens, or a customer API surface unless this changes.

## Roles

- **Staff**: creates orders after physically collecting garments (order does NOT exist before pickup), updates internal status, marks payment collected, views own daily earnings. Scoped to one branch (`users.branch_id`) — the branch whose WhatsApp/phone line they monitor.
- **Admin**: full CRUD on garment catalogue, branches, and staff accounts; can revise order amounts before delivery; manages the monthly billing ledger, aging report, and revenue reports. Can be scoped to one branch (a branch manager) or unscoped (`branch_id = NULL`) to see all branches — build admin views to respect this scope.

## Branches (not "buildings")

A branch is generic: it can be an apartment complex or an area/locality (`branch_type`: `'apartment' | 'area'`). Each branch has its **own phone number and WhatsApp number** — this is the number printed on that branch's marketing/bags and the number customers actually message. Don't assume one phone number for the whole business.

Customers reference a branch (`customers.branch_id`) and a `location_label` (free text — a flat number like "A-304" for an apartment branch, or a house/shop identifier for an area branch). Don't reintroduce a flat-number-only field.

**Per-branch WhatsApp sending — IMPLEMENTED (2026-08-10, migrated to MSG91 same day — see "Messaging migration" below).** Every branch's customer/admin WhatsApp messages send from that branch's own `whatsappNumber`, not one shared number. `src/lib/msg91Client.ts::sendWhatsAppTemplate` takes an explicit `fromNumber` (MSG91's `integrated_number`) — callers resolve it via `resolveWhatsappFrom(branchWhatsappNumber)`, which falls back to the shared `MSG91_INTEGRATED_NUMBER` only when a branch has no number configured yet. `src/utils/roleAwareSelect.ts::customerSelectForRole` always includes `branch: { select: { whatsappNumber: true } }` (not sensitive, so present for both roles) so every `order.customer`/`updatedOrder.customer` fetched through it carries its sending number for free; the three call sites that bypass that helper (`invoiceReissue.service.ts`, `ledgerService.ts::sendReminder`, and `orderService.ts`'s `reviseAmount`/`recordOnlinePayment`) each join `branch.whatsappNumber` explicitly. ## Order workflow (confirmed, updated with client's detailed process confirmation)

1. Customer requests pickup via phone call or WhatsApp — same-day or a scheduled date/time slot.
2. Staff physically visits, collects clothes, categorizes items by garment type from the admin-managed catalogue.
3. System auto-calculates an **estimated amount** from the rate master.
4. **The customer instantly receives a PDF invoice at pickup** — not at delivery. Contains order details, a QR code, and a payment link supporting Card and Net/Online Banking. **This is a confirmed change from the original design** (which generated the invoice on delivery) — invoice generation must trigger on order creation, not on the delivered status transition.

4a. **Admin WhatsApp pickup notification — IMPLEMENTED (2026-08-10).** When staff confirms the item count at pickup (order creation), the branch-scoped admin(s) for that order's branch — or every unscoped/global admin if the branch has none of its own — get a WhatsApp message too, not just the customer. `orderService.ts::createOrder` queries `prisma.user.findMany({ where: { role: 'admin', id: { not: input.createdById }, OR: [{ branchId: null }, { branchId: input.branchId }] } })` (same branch-resolution pattern `reviseAmount`'s existing "Amount Revised" push notification already uses, and excludes the creator themselves the same way, for the case an admin logs a pickup directly) and sends via the new `notificationService.ts::notifyAdminsOfPickup`. Deliberately **WhatsApp only, no SMS, no `communications_log` row** — this targets internal admin `User` rows, not a customer; the "both channels always fire" non-negotiable above is specifically about customer-facing notifications, and `communications_log.customer_id` is a required FK with no admin-notification concept (same reasoning push notifications via `pushService.ts` already don't log there either). Sent from the order's branch's own WhatsApp number (see "Branches" above). Tests: `src/__tests__/orderService.test.ts`'s "createOrder — admin pickup notification" block (query construction, correct fromNumber, no-admins-found no-op), `src/__tests__/notificationService.test.ts`'s `notifyAdminsOfPickup` block (per-admin send, one admin's failure doesn't block the others).

5. Order status becomes **Picked/Pending** (this is the only pre-delivery status the customer sees). Internally, staff/admin can track finer sub-stages — keep `internal_status` separate from the customer-facing status; derive the customer-facing label in application code rather than storing it as a second column that can drift out of sync.
6. **Before delivery, admin may revise the final amount.** If revised: log old amount, new amount, reason, and who changed it (`order_amount_revisions`), and send the customer a WhatsApp message (see "Messaging migration — MSG91, WhatsApp-only" — SMS is no longer sent) with the revised amount and the reason.
7. At delivery, the executive **verifies payment status** and marks the order both **Delivered** and **Payment Received**. Supported payment modes, confirmed as four distinct types: **Cash, UPI, Net Banking, Credit Card** — `paymentMethod` needs to support all four distinctly, not the earlier two-value `qr_online | cash`.
8. Customer/order/payment/delivery data is kept **separately per flat** via `Customer.locationLabel` + `branchId`. **Partially superseded (2026-07-25, see "Customer phone number uniqueness — RESOLVED" below)**: this no longer means a phone number can span multiple flats — `Customer.phoneNumber` is now globally unique, one phone number = one customer/flat, period.

**Not in scope right now**: discounts/coupons and monthly billing (client explicitly confirmed **daily payments only, currently** — the ledger/monthly-billing system stays in the schema for a future release but must not be reachable in the UI yet). Staff auto-assignment/dispatch still not needed at 1–2 staff per branch.

**Future feature, confirmed by client**: monthly plans and discounts will likely be introduced later, and must be **visible/manageable only by Admins** when they are. Don't build this now — just don't design anything that would make adding it later harder.

## ⚠️ Major pricing model update — replaces the earlier catalogue entirely

The client sent a second, much more comprehensive rate card (`garments-seed-data-v2.json`, 106 items) that **structurally supersedes** the first price list, not just adds to it. This needs real schema changes, not just new seed rows:

1. **A brand-new per-KG bulk pricing tier** ("Laundry Services (Per KG)": Wash & Fold ₹125/kg, Wash & Steam Iron ₹150/kg, Premium Laundry ₹200/kg) with a **5kg minimum charge per order**. `GarmentCatalogue` needs a `pricingUnit` field (`per_piece | per_kg`), and `OrderItem` needs to support a weight-based line (`weightKg` + price-per-kg) alongside the existing piece-based line (`quantity` + `unitPrice`) — an order can plausibly mix both (loose clothes by weight + a saree by the piece). The 5kg minimum is an **order-level** rule, not per-item: if any per-kg items are in the order, total weight across them is charged at a minimum of 5kg even if the actual weight is less.

## Per-flat discounts — RESOLVED

- Discount is a **persistent percentage tied to a flat/customer** (`Customer.discountPercent`), not a per-order coupon. Admin sets/edits it per flat, via an admin-only endpoint separate from the staff-usable customer creation flow.
- **Must not be visible to staff** — enforced at the API response level (never included in any response a staff-role token receives), not just hidden in the mobile UI.
- Shown on the billing document as: subtotal → discount line with the % → **"Amount to be paid"**.

## Tech stack decisions

- Payments: Razorpay, QR-code based (no in-app checkout — there's no customer app to check out in)
- Messaging: MSG91's WhatsApp Business API — WhatsApp only, no SMS (see "Messaging migration — MSG91, WhatsApp-only")
- PDF generation: Puppeteer or React-PDF, run as a background job, never inline with the request that completes an order
- Push notifications: Firebase Cloud Messaging (staff/admin devices only)

## Security baseline

- Auth: phone + OTP, short-lived JWT + refresh token, no passwords

**Refresh-token session — IMPLEMENTED (2026-08-10), closes a gap this line described as intent for a long time without it actually existing.** Confirmed via direct question: session duration is a **fixed 2 days from login**, not a rolling/sliding window — the refresh token is never re-signed or extended on use, so it expires exactly 2 days after the OTP that issued it, regardless of how active the session was in between.
- `src/config/index.ts`: new `JWT_REFRESH_EXPIRES_IN` (default `'2d'`), alongside the existing `JWT_EXPIRES_IN` (access token, unchanged default `'30m'`).
- `authController.ts::verifyOtp` now issues both an access token (`createAccessToken`, payload gains `type: 'access'`) and a refresh token (`createRefreshToken`, payload is deliberately minimal — just `userId` + `type: 'refresh'`, no role/branchId baked in) — response shape gained a top-level `refreshToken` field alongside the existing `token`.
- New `POST /api/auth/refresh-token` (`authController.ts::refreshAccessToken`): verifies the refresh JWT, rejects anything not carrying `type: 'refresh'` (so an access token can't double as a refresh token), re-fetches the user from the DB by `userId` (401s if gone) and mints a **fresh access token only** — role/branchId are read live from the DB on every refresh, not cached from login, so a mid-session role/branch change takes effect on the next silent refresh rather than staying stale for up to 2 days. The refresh token itself is never reissued/rotated here — that's what keeps this a fixed window rather than a rolling one.
- `middleware/auth.ts::authenticate` hardened to reject a token with `type: 'refresh'` outright — without this, a stolen refresh token could also work directly as a long-lived (2-day) access token instead of only being exchangeable for short-lived ones.
- **Mobile**: `mobile/src/api/client.ts` gained `setRefreshToken`/`setOnAuthExpired` (module-level, same decoupled-from-React-state pattern as the existing `setAuthToken`) and `apiRequest` now catches a `401` on an already-authenticated request, silently calls `POST /api/auth/refresh-token` via a plain `fetch` (not `apiRequest` itself, to avoid recursion), and retries the original request once on success — so an access-token expiry (~every 30 min) is invisible to the user instead of bouncing them back to the OTP screen. If the refresh itself fails (refresh token expired at the 2-day mark, or invalid), `onAuthExpired()` fires — `AuthContext.tsx` registers its own `signOut` there, so the app correctly drops back to the login screen only at the real 2-day session boundary, not on every access-token expiry. `AuthContext.tsx`'s `TOKEN_KEY`/`USER_KEY` `expo-secure-store` persistence gained a third `REFRESH_TOKEN_KEY`; `signIn`'s signature changed to `(token, refreshToken, user)` — `LoginScreen.tsx`'s one call site updated accordingly.
- Tests: `src/__tests__/authController.test.ts`'s new "POST /refresh-token" block (missing token, garbage token, expired token, an access token rejected when presented as a refresh token, unknown user, and the live DB role/branchId re-read on success) plus a new verify-otp assertion that a refresh token is issued and is distinct from the access token. `tsc --noEmit` clean both sides, backend suite **220/220 passing** (was 200).
- Role-based access enforced server-side (not just hidden in the UI) — a staff-role token must be rejected on admin-only endpoints
- Branch-scoped admin filtering happens at the API layer
- Rate-limit OTP requests per phone number; short OTP expiry
- All secrets in environment variables / hosting platform's secret manager — never committed, never in chat, never in this file
- Parameterized queries throughout (Prisma handles this by default — don't drop to raw SQL without care)
- India's DPDP Act: reasonable security safeguards are a live obligation now, not deferred to 2027 — see Technical Design Document Section 6.3
- **Mock OTP for testing/automation (MOCK_AUTH, Maestro screenshot flows, dev testing)**: must be strictly gated to non-production environments, never reachable in a production build under any condition. **Verified, not assumed**: `src/config/index.ts` — `export const MOCK_AUTH = NODE_ENV !== 'production' && getEnv('MOCK_AUTH', 'false') === 'true'` — already correctly gated on `NODE_ENV`, independent of the `MOCK_AUTH` env var's own value. Re-check this specific line if `config/index.ts` is ever refactored — a hardcoded bypass OTP reaching production is a real vulnerability, not just a dev convenience.

## Laundry bag tracking — RESOLVED and implemented

**Design question this note had to answer first**: `Customer.bagIssued`/`bagIssuedAt` is a single boolean + timestamp, not a count or history — that's only enough to answer "has this customer ever been given a bag," not "how many times has it been replaced." Resolution: **issuance and replacement are tracked as two different kinds of event, not the same field reused**:
- **Issuance** happens *once* per customer, ever. `bagIssued`/`bagIssuedAt` flip from `false`/`null` to `true`/`now()` the first time, and **never reset** — there's no "first bag" counter needed because the boolean itself already encodes it: `false` means "hasn't happened yet," `true` means "already happened once." Marking an already-issued customer as issued again is a deliberate no-op (doesn't touch `bagIssuedAt`).
- **Replacement** (lost/damaged) is a *repeatable* event, logged as its own `AdditionalCharge` row (`chargeType: 'bag_replacement'`, fixed `amount: 350`) every time it happens — this is where "how many times has this customer's bag been replaced" actually lives (as a count of rows), not as a second boolean. Reporting a replacement requires `bagIssued` to already be `true` (400 otherwise — can't lose a bag that was never handed over) and does **not** touch `bagIssued`/`bagIssuedAt`, since the customer's one free issuance already happened.

**Implemented.**
- `PATCH /api/v1/customers/:id/bag-issued` (staff + admin — staff need this at the point of pickup) — idempotent, sets `bagIssued: true`/`bagIssuedAt: now()` only if not already issued.
- `POST /api/v1/customers/:id/bag-replacement` (staff + admin) — creates the fixed-₹350 `AdditionalCharge` (`orderId` optional, ties the report to a specific pickup/delivery if given; `description` optional free text). 400s if the customer's `bagIssued` is still `false`.
- `GET /api/v1/customers/:id/bag-replacements` (admin-only) — lists that customer's replacement history, used to show a count.
- All three in `src/controllers/customerController.ts` / `src/routes/customers.ts`.

**Mobile**: `NewOrderEntryScreen.tsx` shows a "Bag Issued" tag or an "Issue Laundry Bag (Free)" button right below the confirmed-customer card (staff is physically at the pickup — the natural moment to hand it over), calling the new `markBagIssued`. `CustomerManagementScreen.tsx`'s edit modal gained a "Laundry Bag" section (status text + issued date, replacement count fetched via `fetchBagReplacements`) with a "Report Lost / Damaged (₹350)" button when issued, or a "Mark Bag Issued" button when not — admin can do either, not just staff, since the backend allows both roles on both write endpoints.

**Invoice wiring — now IMPLEMENTED, closing the gap this section used to flag.** Client's instruction: wire the ₹350 charge to the invoice "only if it is not the first one... from the second bag onwards" — read as clarifying, not adding a new exemption: the free initial bag (the customer's first bag) was never a charge to begin with, so there's nothing to exclude there; every actual *replacement* (numerically the customer's second bag onward) now gets added to the invoice. There's no "first replacement is free" rule anywhere — every `bag_replacement` `AdditionalCharge` row is billed.

**Implemented.** `invoiceService.ts::generateInvoice` now looks up `AdditionalCharge` rows with `chargeType: 'bag_replacement'` **tied to that specific order** (`orderId` match) and adds their total on top of the discount-adjusted subtotal — flat, not discounted, since a lost bag isn't a laundry service. `invoicePdfService.tsx` gained an `additionalChargesTotal` line, itemized separately from the discount line ("Additional Charges" row before "Amount to be paid") rather than silently folded into a bigger number with no explanation. `customerController.ts::reportBagReplacementHandler` now also triggers `reissueInvoice(orderId)` when the report is tied to an order that isn't yet delivered/paid — same shared reissue function discount changes and amount revisions already use — so the customer's payment link reflects the ₹350 immediately, not on some later unrelated trigger.

**Still open, unchanged from before**: a replacement reported *without* an `orderId` (customer calls in separately, no pickup/delivery context) still has nothing to attach to — that's the same "does it attach to the next order, get billed standalone, wait for the monthly statement" question this section originally raised, and it's still genuinely unanswered. Only the order-tied case was asked for here.

Tests: `src/__tests__/customerController.test.ts`'s "bag-issued"/"bag-replacement"/"bag-replacements" blocks (idempotency, 404s, the bagIssued-required-first validation, the fixed ₹350 amount, role gates, and new: reissue fires when tied to an open order, doesn't fire when delivered/paid or untied) and `src/__tests__/invoiceService.test.ts`'s new "bag-replacement charges tied to this order" block (single charge, multiple charges summed, charge added after discount not before, no charge when none exist).

## Mobile testing fixes (2026-07-25) — scroll bugs, no logout, MOCK_AUTH always admin, stale DATABASE_URL

Found while the client tested the running app directly, not from a code read:

**Scroll bug: 4 admin list screens didn't actually scroll.** `GarmentCatalogueScreen.tsx`, `BranchesScreen.tsx`, `StaffManagementScreen.tsx`, and `CustomerManagementScreen.tsx` all used `AppScreen scroll={false}` with the list `.map()`'d directly into a plain `View` — nothing scrollable wrapped it, so with the catalogue at 192 items only whatever fit on one screen was reachable. **Fixed**: each list is now wrapped in its own `ScrollView` (`styles.listScroll`, `flex: 1`), with the "+ Add ___" button staying outside/below it so it's always reachable regardless of scroll position.

**Correction (2026-07-25): that fix was incomplete — client reported Garment Catalogue was still stuck at 5-6 visible items with no scroll after it.** The `ScrollView` wrap was necessary but not sufficient. Real root cause: react-native-web's CSS flexbox gives every `flex: 1`/`flexGrow: 1` container a default `min-height: auto`, which floors that container's height at its *content's* natural size rather than letting it shrink to the space actually available — so each nested `flex: 1` `View` between `AppScreen` and the `ScrollView` just grew to fit all 192 items instead of clipping to the viewport, and the `ScrollView` never received a genuinely bounded box to scroll within. Expo's own web `index.html` deliberately sets `body { overflow: hidden }` specifically so `ScrollView`s handle all scrolling themselves — so once the outer chain refuses to clip, there's no fallback page-level scroll either, matching exactly "can only see 5-6 items, no way to scroll further."

**Fixed properly**: `minHeight: 0` added at every `flex: 1` level in the chain — `AppScreen.tsx`'s shared `body`/`content` styles (fixes this for every `scroll={false}` screen at once, not just the four already touched) plus each individual screen's own `body`/list-wrapper style, for belt-and-suspenders correctness since the floor applies independently at each nested level. ## App icon — implemented, but built from a placeholder mark, not the real client logo

**Important caveat, checked directly before touching anything**: the colors used here (`#F56D3E` peach / `#032969` navy) are **not verified client-final colors** — they came from a pasted SVG/prompt claiming a prior "pixel-extraction from `peachandBlue_image.jpeg`" that does not exist anywhere in this repo (checked: no such file exists; the only logo asset is the same `images/peachandBlue_image.ai` this file already flags as an unusable legacy EPS export with no embedded preview/color data). `mobile/src/theme/theme.ts` still uses the original placeholder `#F2764A`/`#16305C` — **this app-icon work did NOT touch the app's theme colors**, only the app icon/favicon assets, and only because real, literal SVG markup was pasted directly into the conversation (not just described) — that's real, usable input regardless of whether its color values turn out to be the final brand palette. If the client's real colors turn out to differ, both this icon and `theme.ts` need reconciling together at that point.

**What was actually built vs. what the request assumed already existed**: the request referenced `app_icon_PB_twotone_1024.png`, `icon_android_adaptive_foreground.png`, and `peachandblue_logo_transparent.png` as if already present in the repo — none existed. The only real asset provided was one plain SVG (`app_icon_PB_twotone.svg`: "P" + "&B" text, Georgia serif, on white) — saved to `mobile/assets/app_icon_PB_twotone.svg`. Two other images shown in the same message (an ornate serif "Peach & Blue" wordmark and an overlapping "P&B" monogram) were **rendered previews only, not real files** — no bytes/source were ever attached for those, so they were not used and nothing was fabricated to match them.

**Implemented.** Since Expo's `app.json` `icon`/`adaptiveIcon` fields require PNG, not SVG, and this environment has no SVG rasterizer (no ImageMagick/Inkscape — same gap flagged earlier for the `.ai` file), added `sharp` as a mobile devDependency (`npm install --save-dev sharp` — a real, one-time dependency, not removed after use, since it's the one working rasterization path in this environment and may be needed again for future asset regeneration) and wrote `mobile/assets/_generate-icons.js` (not wired into any npm script, run manually) to rasterize the one real SVG into all four PNG assets that actually needed replacing:
- `icon.png` — main app icon, mark trimmed/recentered (the SVG's own baked-in text coordinates rendered badly off-center in this environment's font metrics, so the script trims to the real rendered bounding box and recenters in code rather than trusting the SVG's x/y) at ~78% of the canvas, white background.
- `android-icon-foreground.png` — same trim/recenter, sized to ~60.5% of the canvas (Android's adaptive-icon safe zone is 72dp/108dp ≈ 66.7% — confirmed against the actual SDK 57 docs via `WebFetch`, not assumed — 60.5% sits safely inside it), transparent background. Verified programmatically (raw pixel sampling, not just visual inspection) that the corner is genuinely alpha `0` and the mark is opaque — a `Read`-tool preview alone can't distinguish real transparency from an opaque-white PNG.
- `android-icon-monochrome.png` — the Android 13+ Material You themed-icon variant, previously still Expo's stock placeholder glyph (confirmed by viewing the file before touching it); regenerated with the same mark since Android re-tints this layer itself regardless of source color.
- `favicon.png` — same "still Expo's stock placeholder" situation, same fix.

`app.json` changes: `android.adaptiveIcon.backgroundColor` changed from Expo's stock `#E6F4FE` to `#FFFFFF`, and `backgroundImage` (pointing at Expo's stock placeholder background art, confirmed by viewing it before removing) was **removed entirely** — confirmed via the real SDK 57 docs (`WebFetch`) that `backgroundImage` overrides `backgroundColor` when both are set, so leaving it in place would have silently kept showing the old placeholder background regardless of the color change. `icon`/`foregroundImage`/`monochromeImage` paths were left unchanged since the generated files were written in place at those same existing paths.

**Not done, and not fabricated**: `peachandblue_logo_transparent.png` (a general-purpose in-app logo image, separate from the app icon) was not created — there is no real source file for the fuller wordmark design shown in the two preview images, only the small "P&B" monogram SVG. Producing a "transparent logo" asset would have meant guessing at a design that was never actually provided as real data. `mobile/src/theme/theme.ts`'s color placeholders were also deliberately left untouched, per the caveat above.

Verified: `npx tsc --noEmit` clean in `mobile/`, `app.json` confirmed valid JSON, all four generated PNGs visually inspected via the `Read` tool.

## Light/dark mode — Implemented, defaults to light

`mobile/src/theme/theme.ts` exports `lightColors`/`darkColors` (a `ColorTokens` shape both must satisfy) instead of one static `colors` object. Some tokens are deliberately identical across both palettes rather than flipping: `peachPrimary`/`peachPrimaryDark`/`white` (brand accent + button-label text), `chrome` (the dark navy bar used for every app bar/footer/tab bar/total bar — already dark in light mode, doesn't need to get "darker"), and `cream` (light header-title text sitting on that fixed `chrome` bar). Everything else (`peachBg`, `peachCard`, `surface`, `navy`, `navyText`, `navyDeep`, `border`, `muted`, `successBg`, `warningBg`) flips. `mobile/src/context/ThemeContext.tsx` (mirrors `AuthContext.tsx`'s conventions) holds the mode, persisted via `expo-secure-store` (no AsyncStorage dependency added), default `'light'`. A new `mobile/src/screens/shared/SettingsScreen.tsx` houses the toggle plus the About-page content this file separately required ("Technology by NIVENXA") — bundled into one screen since neither existed before, registered in both `AdminStack`/`StaffStack`, reachable via a settings icon on the Admin/Staff home app bars. `app.json`'s `userInterfaceStyle` changed from `"light"` to `"automatic"` so native iOS chrome (keyboard, alerts) doesn't clash with an in-app dark theme.

Small fixed-pastel "chip" badges (`theme/serviceTag.ts`'s service tags, `BranchesScreen.tsx`'s apartment/area tags) intentionally keep their existing background+foreground pairing across both themes rather than following the flipping tokens — they're small, self-contained, already-contrasted elements, not full surfaces.

Not built: OS-appearance-following ("system") mode — this is a manual `'light' | 'dark'` toggle only, not asked for beyond that.

**UX change: moved off the Settings screen, per client's explicit preference for a direct icon toggle over a navigation trip.** `SettingsScreen.tsx`'s two-button Light/Dark row is gone — `mobile/src/components/ThemeToggle.tsx` is a compact pill switch (sun/moon `MaterialCommunityIcons`, animated sliding knob via `Animated.timing`, `ThemeContext`'s existing `toggleMode()`) placed directly in `AdminDashboardScreen.tsx`'s and `StaffHomeScreen.tsx`'s app bars, next to the settings gear button — one tap flips the theme from wherever the user already is, no screen navigation required. `SettingsScreen.tsx` now holds About-page content only. Fixed (non-theme-reactive) colors, same treatment as the settings button it sits beside, since both always render on the permanently-dark `chrome` app bar.

## Automated screenshot capture (Maestro) — built, not yet run end-to-end

`mobile/.maestro/staff-flow.yaml` and `admin-flow.yaml` + `mobile/scripts/capture-screenshots.js` (`npm run screenshots` in `/mobile`) drive the app through login and every main screen for each role and save numbered screenshots to a timestamped `mobile/screenshots/<timestamp>/` folder, so regenerating a client-facing batch is one command. Full details, required env vars, and the data-side-effect warning (the staff flow creates one real "Maestro Screenshot Test" customer row in the live `customers` table so the garment picker has something to unlock — stops before "Confirm Pickup" so it never creates a real order) are in `mobile/.maestro/README.md`, not duplicated here.

Added `testID`s to `LoginScreen.tsx` (phone/OTP inputs, role toggle, submit button) and `NewOrderEntryScreen.tsx` (phone search, new-customer name/location/confirm, garment search) specifically so these flows have stable selectors instead of relying on layout-relative matching — no behavior change.

**Real blocker found while building this, not glossed over**: this project has no standalone native build. `mobile/README.md`'s own setup instructions run it inside Expo Go, and `app.json` has no `android.package`/`ios.bundleIdentifier` configured — `expo prebuild`/an EAS build has never been run. Maestro automates installed native apps by `appId`; it cannot drive `expo start --web` at all. `mobile/.maestro/README.md` documents two ways around this (target Expo Go directly via an `exp://` deep link — no native build needed — or configure a real package/bundle id and build a dev client, better for CI but a real product decision, flagged rather than picked silently since it's also the eventual app-store identifier).

Separately, this specific dev environment (Windows, no WSL) could not run any of it to verify: confirmed via `curl -Ls https://get.maestro.mobile.dev | bash` that the installer itself runs here but refuses to proceed — no Java on this machine — and separately confirmed no Android SDK, no `adb`, no emulator; iOS simulators don't run on Windows at all regardless. Nothing was installed, nothing was launched. The flow files are reviewed against the actual current screen code (selectors, tab labels, button text all verified by reading the real source, not assumed) and `mobile`'s `tsc --noEmit` is clean, but need a real run against a booted simulator/emulator — your machine, a teammate's Mac, or CI — to confirm the selectors and conditional branches (existing-vs-new customer, order-card-present-vs-not) actually hold up.
